# Elite State CFW — Discord + Vercel

نسخة 1.2: الدخول بحساب Discord، والوصول حسب رتب السيرفر. لا يوجد تسجيل بالبريد أو كلمة مرور خاصة بالموقع، ولا يحتاج هذا المسار SMTP. تبقى PostgreSQL وSupabase مسؤولتين عن البيانات والجلسات.

**حالة النسخة:** ملفات جاهزة للربط والنشر، مع اختبارات محلية. لم يتم تفعيل التطبيق على حساب Discord أو Vercel فعليًا، ولم تُختبر جلسة Discord حقيقية. الموقع السابق وبياناته لم تتغير.

## الرتب والصلاحيات

| الرتبة المبدئية | الصلاحيات المبدئية |
|---|---|
| Owner، Co-Owner، Founder، Co-Founder، «ال تيمات»، EL\|Administration Manager | إدارة محتوى الأقسام، النشر والأرشفة، جميع البلاغات والمهام، سجل العمليات وإعدادات الروابط |
| هاي مانجمنت | التعليمات والإعلانات كمسودات، متابعة جميع البلاغات والمهام، وعرض الطاقم؛ دون صلاحية نشر افتراضية |
| مانجمنت | عرض المحتوى المنشور، إنشاء البلاغات، متابعة سجلاته والمهام المسندة إليه |
| مالك الموقع | جميع الصلاحيات، إضافة روابط الرتب وتعديلها، وإيقاف الأعضاء محليًا |

الأسماء للتوضيح فقط. **كل رتبة تبدأ بدون ربط ولا تمنح دخولًا حتى يضيف المالك Discord Role ID الصحيح.** اسم «ال تيمات» محفوظ كما كتبه المستخدم مؤقتًا؛ يمكن تعديله أو تقسيمه إلى أكثر من رتبة.

رتبة اسمها Owner في Discord ليست ملكية الموقع. مالك الموقع حساب واحد مثبت برقم Discord ثم بمعرّف Supabase؛ لا يمكن نقله أو إيقافه من واجهة الطاقم. تعديل ربط الرتب والعضوية محصور بهذا الحساب.

كل رتبة قابلة لتعديل صلاحياتها من اللوحة. عند امتلاك عدة رتب، تُستخدم رتبة واحدة بالأولوية الأعلى، وليس مجموع الصلاحيات. عند تساوي الأولوية يُحسم الترتيب بالمعرّف الداخلي؛ يفضّل ضبط أولويات مختلفة عند اختلاف الصلاحيات.

من يملك صلاحية منح إحدى الرتب المعتمدة في Discord يستطيع عمليًا منح وصول للموقع. اضبط صلاحيات Manage Roles في سيرفرك وفق ذلك.

## خطوات الربط

### 1. حدّث قاعدة البيانات الموجودة

إذا نفّذت ملف `001-initial.sql` سابقًا، شغّل الآن **محتوى `database/002-discord.sql` فقط** في Supabase SQL Editor. هذا يضيف ربط Discord ويحافظ على السجلات.

للمشروع الجديد، شغّل 001 ثم 002. بديلًا عن SQL Editor، بعد ضبط `.env.local` شغّل `npm run db:migrate`؛ ينفّذ الملفين داخل معاملة واحدة. لا تشغّل الترحيل تلقائيًا مع كل بناء.

المخطط `elite` خاص بالخادم، وRLS مفعّل بدون سياسات عامة. لا تضفه إلى Exposed schemas ولا تمنح `anon` أو `authenticated` الوصول إليه.

إذا أُسست نسخة البريد القديمة بالفعل، لا يتبنى الكود مالكها تلقائيًا من البريد: يلزم ترحيل هوية صريح ومراجع. إنشاء الجداول وحده بدون تأسيس مالك قديم لا يحتاج هذه الخطوة الإضافية.

### 2. أنشئ تطبيق Discord

1. افتح [Discord Developer Portal](https://discord.com/developers/applications).
2. أنشئ تطبيقًا باسم Elite State CFW، وراجع شروط Discord بنفسك.
3. في Supabase افتح Authentication → Sign In / Providers → Discord، وانسخ Callback URL المعروض هناك.
4. في تطبيق Discord، من OAuth2 أضف رابط Callback المنسوخ إلى Redirects واحفظه. شكله `https://<project-ref>.supabase.co/auth/v1/callback`؛ هذا **ليس** رابط Vercel.
5. انسخ Client ID وClient Secret مباشرة إلى حقلي مزوّد Discord في Supabase وفعّله. Client Secret سري؛ لا ترسله في الدردشة ولا تضعه في كود الواجهة.
6. من قسم Bot أنشئ البوت إن لم يكن موجودًا، واحفظ Bot Token بأمان لإضافته إلى Vercel لاحقًا. توكن البوت مختلف عن Client Secret.
7. ثبّت البوت في سيرفرك باستخدام تثبيت Guild أو OAuth2 URL Generator مع نطاق `bot`. هذا التطبيق يحتاج قراءة عضوية مستخدم محدد فقط؛ لا تمنح البوت Administrator أو Manage Roles أو صلاحيات قراءة الرسائل.

البوت لا يرسل رسائل ولا يغيّر رتب Discord. يستخدم الموقع طلب REST لقراءة العضوية؛ لا يحتاج برنامج بوت دائم الاتصال بالـGateway لهذا العمل.

مرجع: [تفعيل Discord في Supabase](https://supabase.com/docs/guides/auth/social-login/auth-discord)، [Discord OAuth2](https://docs.discord.com/developers/topics/oauth2).

### 3. إعدادات Supabase Auth

- فعّل Discord.
- بعد التأكد من إعداد Discord، عطّل **Enable email provider** داخل Email لإيقاف الدخول والتسجيل بكلمة المرور على مستوى الخدمة أيضًا.
- أبقِ **Allow new users to sign up** مفعّلًا لحسابات Discord الجديدة.
- أبقِ **Allow anonymous sign-ins** و**Allow manual linking** غير مفعّلين.
- لا تحتاج إعداد SMTP أو قوالب البريد لتسجيل الدخول بـDiscord. قد يطلب Discord نفسه تأكيد حساب المستخدم حسب إعداداته.
- لا تستخدم مفتاح service_role في الواجهة. التطبيق يحتاج Publishable key فقط في المتصفح.

### 4. إعداد Vercel

ارفع **ملفات نسخة Discord الجديدة** إلى مشروع Next.js على Vercel. لا تستخدم ملف ZIP القديم الخاص بالبريد، ولا تكتفِ بوضع الملفات بجانب `index.html` في مشروع ساكن. يجب أن يكون جذر المشروع هو المجلد الذي يحتوي `package.json` و`app`.

يمكن الاستيراد من مستودع Git خاص بك، أو تشغيل `npx vercel login` ثم `npx vercel link` من مجلد المشروع. لا ترفع أسرار `.env.local` أو `node_modules` أو `.next`.

أضف في Vercel → Project Settings → Environment Variables:

| المتغير | المطلوب |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Project URL من Supabase |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | مفتاح Publishable العام فقط |
| `DATABASE_URL` | اتصال PostgreSQL Transaction pooler من Supabase، مع كلمة مرور قاعدة البيانات. سري |
| `DATABASE_SSL_CA` | اختياري: شهادة الجذر PEM من Supabase إذا احتاج اتصال TLS ذلك |
| `NEXT_PUBLIC_APP_URL` | رابط الإنتاج النهائي في Vercel، مثل `https://your-project.vercel.app` |
| `DISCORD_GUILD_ID` | رقم سيرفر Discord الذي يحتوي الطاقم والبوت |
| `DISCORD_OWNER_ID` | رقم حسابك أنت الذي سيمتلك الموقع؛ ليس رقم رتبة |
| `DISCORD_BOT_TOKEN` | توكن البوت، سري وخادمي فقط |

لم تعد النسخة تستخدم `INITIAL_OWNER_EMAIL`. أرقام الرتب تُحفظ من واجهة المالك، فلا تحتاج متغير استضافة لكل رتبة.

لنسخ الأرقام، فعّل Developer Mode في إعدادات Discord، ثم استخدم Copy Server ID وCopy User ID وCopy Role ID من قوائم العناصر المناسبة. استخدم أرقامًا كنصوص، وليس أسماء أو منشن مثل `<@&...>`.

Client Secret يوضع في Supabase فقط، وBot Token يوضع في Vercel فقط. لا تستخدم لأي منهما بادئة `NEXT_PUBLIC_`. لا تضعهما في هذا الدليل أو مستودع Git أو محادثة.

الإطار **Next.js**، وأمر البناء `npm run build`، ومجلد الإخراج تلقائي. اختر Node.js مدعومًا 22.13 أو أحدث. بعد حفظ المتغيرات أعد البناء والنشر؛ متغيرات `NEXT_PUBLIC_*` تحتاج بناء جديدًا.

في Supabase → URL Configuration:

- Site URL = رابط Vercel نفسه الموجود في `NEXT_PUBLIC_APP_URL`.
- Redirect URLs = رابط Vercel متبوعًا بـ `/auth/callback`.
- أضف النظير المحلي فقط إذا احتجت التطوير، مثل `http://localhost:3000/auth/callback`.
- لا تستخدم سماحًا عامًا لكل النطاقات.

افصل بيئة Preview عن أسرار وقاعدة إنتاج حقيقية. على النطاق العام المقصود، تأكد من أن Deployment Protection في Vercel لا يطلب حساب Vercel من إدارييك؛ حماية التطبيق نفسها تظل مطبقة. راجع تكلفة وحدود خططك قبل اختيار أي خدمة مدفوعة.

### 5. التأسيس ومنح الصلاحيات

1. افتح الموقع وسجّل بحساب Discord الذي رقمه يطابق `DISCORD_OWNER_ID`، ويجب أن يكون عضوًا في السيرفر.
2. اضغط «تأسيس لوحة Elite State».
3. افتح «الرتب والصلاحيات». ستجد الرتب المطلوبة، لكن روابطها فارغة عمدًا.
4. عدّل كل رتبة، وألصق **Role ID** الصحيح من Discord وحدد صلاحياتها وأولويتها ثم احفظ. لا تستخدم رقم السيرفر نفسه؛ هذا هو رقم رتبة everyone.
5. امنح الإداري الرتبة في Discord وأرسل له رابط الموقع. بعد الدخول يضغط «تفعيل العضوية والدخول».
6. لسحب الوصول، اسحب جميع رتبه المرتبطة باللوحة في Discord، أو أوقفه محليًا من الطاقم. وجود رتبة مسموحة أخرى يظل يمنحه صلاحياتها.
7. إلغاء الإيقاف المحلي لا يكفي وحده؛ يجب أن تعود عضوية Discord والرتبة المسموحة أيضًا.

## آلية الحماية وحدودها

- الهوية تؤخذ من `auth.getUser()` على الخادم، ومن معرّف مزوّد Discord المحمي `identities[].id`. لا تثق في `user_metadata` أو `identity_data.sub` أو البريد أو الترويسات القديمة لمنح الملكية.
- العضوية والرتب تُقرأ من Discord في كل طلب محمي، ولا توجد ذاكرة سماح قديمة عند تعذر الاتصال. انقطاع Discord أو خطأ البوت أو تجاوز الحد يمنع الطلب مؤقتًا.
- سحب الرتبة يمنع **الطلب التالي بعد تطبيق التغيير في Discord**. لا يمكن سحب معلومات سبق عرضها أو نسخها، وطلب بدأ التحقق قبل السحب قد يكمل.
- قائمة الطاقم تعرض العضويات التي فعّلت دخولها وآخر تحقق ناجح. ليست تعدادًا حيًا لجميع أعضاء Discord، و«غير موقوف محليًا» لا يعني أنه ما زال يحمل الرتبة.
- سجل العمليات للقراءة من التطبيق، لكنه ليس سجلًا خارجيًا غير قابل للعبث بواسطة مسؤول قاعدة البيانات.
- لا يوجد ربط مباشر ببيانات اللاعبين أو حظر FiveM داخل اللعبة؛ الموجود روابط السيرفر ولوحة إدارة مستقلة.
- ترقيات الرتب وتخفيضها تُزامن من الربط المعرّف في الموقع. لا تمنح العضو ترقية محلية من نموذج تعديل الطاقم.
- لا تمنح صلاحيات قاعدة البيانات أو البوت لرتب Discord مباشرة؛ فحوص التطبيق هي التي تحدد ما يمكن عرضه وتنفيذه.

## الفحص والتشغيل المحلي

```sh
npm ci
npm run typecheck
npm test
npm run build
npm run dev
```

ضع إعداداتك المحلية في `.env.local` فقط، بناءً على `.env.example`.

الاختبارات تستخدم PostgreSQL محليًا داخل PGlite، مع بدائل اختبار لردود Supabase وDiscord. تشمل الهوية المزوّرة، منع البريد وحده، عدم السماح بالرتب غير المرتبطة، سحب الرتبة وعودتها، الأولوية، حماية المالك، الانقطاع، الملاحظات الداخلية، المعاملات والتحديثات المتزامنة. **هذه ليست تجربة OAuth حقيقية أو اختبارًا لتوكنك أو TLS إلى قاعدة Supabase.**

اختبار HTTP: بعد البناء، شغّل `npm run start -- --hostname 127.0.0.1 --port 3100` ثم `npm run test:http`. طابق عنوان `TEST_BASE_URL` مع `NEXT_PUBLIC_APP_URL` إن كان مضبوطًا.

قبل دعوة الطاقم، جرّب بحسابين حقيقيين: مالك وعضو تجريبي. تحقق من رفض حساب بلا رتبة، ثم نجاحه بعد منحها، وتغير صلاحياته عند تغيير الرتبة، ورفضه بعد سحبها أو إيقافه محليًا. لا تعطّل المنع عند تعطل Discord.

المراجع: [Supabase Discord](https://supabase.com/docs/guides/auth/social-login/auth-discord)، [قراءة عضو Discord](https://docs.discord.com/developers/resources/guild#get-guild-member)، [اتصال PostgreSQL](https://supabase.com/docs/guides/database/connecting-to-postgres)، [Next.js على Vercel](https://vercel.com/docs/frameworks/full-stack/nextjs).
